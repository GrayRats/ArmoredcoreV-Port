# Project Architecture (ACV, Xbox 360)

Revision 2026-10-21. `default.xex` has been extracted, analysed and generated by XenonRecomp. For an independent Linux check of ReXGlue, a private project was created; conditional branch targets were refined against retail bytes, and the generation pass no longer contains any identified unresolved-branch fatal paths. The Linux C++ build has been started; loading the game has not been verified yet. The outputs of the two recompilers are not mixed.

The current target platform is Linux. Windows builds, Wine and Windows-only work are postponed until the user requests them separately. Existing Windows results are kept as historical evidence.

[Русская версия](ARCHITECTURE.RU.MD)

## Principles

1. Every claim has an address, a source and a confidence level (confirmed / hypothesis / not verified). A tool's output is not treated as a property of the game.
2. Code generated by a recompiler is a **machine translation** of PPC into C++ that needs a separate runtime to run on x64 (Windows/Linux). It is not a recovered source. Unity/C# is not required for decompilation.
3. The emulator (Xenia) is the reference for behaviour used for comparison, not a part of the product.
4. Data and tools are isolated per game: ACV is the only confirmed title.

## Layers

```
L0 Sources and evidence
   ISO/XEX -> tmp/scan/{text,pdata}.bin -> Ghidra (RPC & MCP) -> tools/xref_index.py -> logs/decomp.sqlite3 (operations/index)
   diagnostics -> logs/errors.sqlite3; output/archive -> logs/output.sqlite3; provenance/cleanup -> logs/artifacts.sqlite3
   Xenia Edge: trace (log_lr_at_instruction), guest memory reads (/proc/pid/mem)

L1 Static recompilation of code          (XenonRecomp)
   XenonAnalyse -> switch TOML -> XenonRecomp (+ ppc_context.h) -> C++ shards
   Input: function list (.pdata + leaf functions without .pdata), register-save helper addresses, switch tables

L2 Shader recompilation                  (XenosRecomp)   [sources present, not built]
   Xbox 360 shader binary -> HLSL/SPIR-V; requires a shader set extracted from the game

L3 Host runtime for recompiled code      [partial isolated native C++ probe]
   guest memory map, kernel/xam imports, threads, graphics, input, filesystem
   Needed separately for the current XenonRecomp workflow; the installed ReXGlue runtime is not yet integrated with it.

L4 Comparison (oracle)
   recompiled function <-> Xenia: same input registers/memory -> same outputs

L5 Reconstruction / integration (optional goal)
   Readable C++ and semantic checks; Unity/C# only if needed
   Assets and the game engine are not part of the mandatory decompilation criteria
```

## Architecture decisions (proposal, requires confirmation)

1. **Recompilation is the main analysis path**, not an automatic delivery target. L4 compares small functions with the same inputs/outputs in a generated/native harness and in Xenia. Unity/C# is added only if separately needed.
2. **L1 coverage.** The XenonRecomp baseline reported 10,939 unsupported addresses; the isolated `BBB_MoreInstructions` left 38. The ordered lookup in Xenia classified raw words as `frsqrtex` (24), `vnor128` (3), `vsldoi128` (1), `lhbrx` (8), `mulhdx` (2). Isolated changes added `vnor128`, removed the PPC403 alias for Cell/Xenon and added `lhbrx`, `mulhdx`; diagnostics dropped to 24 (`frsqrte`). Host probes: `vsldoi128` all 16 shifts, `vnor128` 1,048,576 lanes, `lhbrx` 3 aligned halfwords, `mulhdx` 9 signed cases. These are narrow code and generation checks, not an Xbox 360 trace, a full-shard build or runtime verification. Open: confirm a Xenon-compatible estimate of `frsqrte`. Switch `0x82EF87B0` is resolved: the signed `addi` gives the base `0x82EF87B4`; all 29 targets are inside the owner's `.pdata`, and the TOML was accepted by separate generation. Details: [XENONRECOMP.md](fine/XENONRECOMP.md) and [XENON_MORE_INSTRUCTIONS.md](fine/XENON_MORE_INSTRUCTIONS.md).
3. **A single function registry.** One file (`tmp/functions.json`, later `logs/functions.sqlite`) with fields: address, length, source of the boundaries (`.pdata` / heuristic / manual), whether it is a leaf owner, recompilation status, comparison status. Right now the boundaries are spread across `.pdata`, Ghidra and xref; a mismatch has already caused an error (the `mftb` binding to the wrong function, see "Correction" in `PROGRESS.md`).
4. **Quality gates.** Any result that uses the call graph must be checked against leaf functions without `.pdata` and against indirect calls (`bctrl`, vtable); a graph built only from `bl` is a lower bound.
5. **Tools by external authors:** sources in `tools/<name>/`, builds in `tmp/<name>-build/`, local settings in separate files. Do not mix code generation and runtime of different projects without checking compatibility.

## Verified first step of L3

`tools/native-host-probe/` preserves the ABI of the existing hedge-dev XenonRecomp: `PPCContext&, uint8_t* base`. The 4 GiB reservation, checked guest pages, big-endian load/store and the dispatcher work for two isolated call-free functions `0x822B0818` and `0x822B0820`. Clang + UBSan: 41 checks passed; the Windows backend via VirtualAlloc/VirtualFree passes the same 41 checks under Wine. This is not a test on real Windows; the RTTI diagnostic for the static link remains. Full shards were not compiled; the XEX was not loaded and the entry point was not called. This is a synthetic CPU/memory probe, not an L4 comparison with Xenia and not a confirmation of ACV compatibility. Details and limitations: [NATIVE_HOST_L3.md](fine/NATIVE_HOST_L3.md).


## Execution control and logs

`tools/decomp-logging/` keeps operations/tasks in `logs/decomp.sqlite3`, diagnostics in
`logs/errors.sqlite3`, compressed full output and the log archive in
`logs/output.sqlite3`, and the cleanup catalogue/history in `logs/artifacts.sqlite3`.
Existing IDs and tables of the main database are preserved; old event/artifact records
are reflected in separate files. Old stdout/stderr previews are marked as incomplete.

The shared scripts `decomp.sh`, `ghidra-rpc.sh`, `assets.sh` and `unity.sh` automatically
go through the common runner. Other commands run through `cli.mjs run`; results of direct
MCP calls are saved and passed to `ingest`. The policy for future agents is in the root
`AGENTS.md`. There is no interception of arbitrary external processes.

Legacy log files are imported as a stream; compressed chunks are verified by reading back
and by SHA-256. Cleanup keeps registered/referenced evidence and deletes only exact
duplicates with a verified archive and an audit record. SQLite WAL does not guarantee
atomic crash recovery across several files; indexes and diagnostics are reconciled again
by IDs, and unfinished streams stay marked. Procedures and real limitations:
[SQLITE_LOGGING.md](SQLITE_LOGGING.md).

## ReXGlue Linux — current state, 2026-10-21

The initial ReXGlue 0.10.0 generation produced 625 C++ files but exposed 95
conditional branches to 19 destinations. Original-byte listings show that 18 targets
are `li r3,0; blr`, and `0x82500F14` is `lis/addi/blr`; none has a `.pdata`
owner. Supplemental byte-backed fragment extents are recorded in
`tools/native-rexglue/acv-conditional-targets.toml` without asserting parent
function ownership. A separate output generation took 492 seconds; an audit of
all 311 C++ units found 19 definitions and zero unresolved-branch `REX_FATAL`
placeholders. Evidence: `logs/acv-rexglue-unresolved-20261021/conditionals/`;
verified generation operation `3d924902-d86e-4ebf-bcf2-7cc96efd1f42`.

CMake is configured for `generated/conditional-fragments`. The Linux Clang/Ninja
build is active and currently repeats codegen to register the generated depfile
before compiling. After the build, perform a bounded launch with `tmp/iso_root`,
inspect the logs, and verify the XEX entry, graphics, resources and gameplay. The SDK
source audit found 40 warning-only imported functions; investigate them only if
runtime traces reach them. The full runtime, shaders/audio/input/networking and parity
with Xenia or hardware remain unverified. Windows awaits a separate request; Unity/C#
is not required.

Rough completion estimate (judgement, 2026-10-21): codegen gate ~90%, Linux
build/boot milestone ~45% (build active), broad semantic recovery ~20%, overall
reconstruction ~15% complete / ~85% remaining. These percentages are planning
estimates rather than measured metrics.

## ReXGlue Linux build components — update 2026-10-21

- `tools/native-rexglue/probe_linux.py`: bounded launch wrapper. Options: `--seconds`,
  `--log-level`, `--screenshot-every` (currently `spectacle -a`, to be replaced by window
  capture), `--extra=--cvar=value` (passed to the SDK).
- `tools/native-rexglue/generate_adjusting_thunks.py` → `tmp/acv-native-adjusting-thunks.cpp`
  (63 thunks); `retail_leaves.cpp` for hand-checked leaves.
- `tools/native-rexglue/propose_data_referenced_boundaries.py` →
  `acv-data-referenced-functions.toml` (459 entries). Filters: a separate XenonRecomp
  registry (proposal source only), original-byte CFG contiguity, exits, `.pdata` and
  local-label interiors. Code-materialized pointers (`lis`/`addi` pairs) are included.
- `tools/native-rexglue/audit_data_referenced_codegen.py`: checks registration, definition
  and `REX_FATAL` against the generated tree.
- `tools/native-rexglue/validate_adjusting_thunks.py`: class scan of all `lwz`/`b` pairs.
- `tools/native-rexglue/sample_codegen.sh`: read-only `eu-stack` sampler of the codegen process.
- `tools/rexglue-graph-opt/` (isolated experiment): `indexed/src/codegen/phase_gapfill.cpp`
  replaces the O(G·N) absorb scan; CMake prefers `indexed/` copies of the codegen files.
  Not yet verified against the release output.
- Data flow: original XEX → boundary TOMLs → ReXGlue codegen (`acv_linux_probe_manifest.toml`
  includes all three TOMLs) → generated C++ → CMake Clang build with `retail_leaves.cpp`
  and the thunk file → `acv_linux_probe` → `probe_linux.py`.

## Linux host input adapter — 2026-10-21

The private ReXGlue Linux probe uses the installed SDK's MnK driver as a
synthetic XInput controller for player one. The durable profile is
`tools/native-rexglue/input-profile.json`; `probe_linux.py` supplies its cvars.
The app hook in `acv_linux_probe_app.h` controls mouse capture (F8/Escape) and
retains SDK overlay key processing. No retail PPC function was replaced for
input. This is a host adapter, not a reconstructed game input system.

Optional persistent user data stays under the workspace `tmp/`. Per-run evidence
stays under `logs/acv-native-linux/`, and execution records go into the existing SQLite
ledgers. Error samples and duplicate forwarding are bounded; eight unhandled guest
access violations stop only the child launched by that probe. Raw SDK logging
and rotation remain SDK behaviour. [Controls and validation](LINUX_INPUT.md).
